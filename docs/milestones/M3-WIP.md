## Decisions & trade-offs
<!-- design decisions as they're made, with alternatives considered -->

### D1 — Outbox payload: app-serialized Avro bytes, passthrough converter
The outbox adapter maps domain event → Avro wire class (reusing M2's
`OrderEventMapper`) and serializes with the same Confluent
`KafkaAvroSerializer` M2 uses → Confluent wire format (magic byte + schema
ID + Avro binary) stored in `payload BYTEA`. Connect uses a byte-array
passthrough value converter (exact class confirmed in step 7).
- **Why:** bytes on `order-events` are identical to M2's direct publish —
  consumers see no change; schema validated at write time against the
  reviewed, registered schema (`auto.register.schemas=false` preserved);
  no Avro converter JARs needed in the Connect image.
- **Accepted costs:** payload unreadable via `psql` (use Kafka UI);
  Schema Registry in the write path (mitigated by serializer schema-ID
  caching; HA registry in prod).
- **Rejected — JSON payload + `expand.json.payload` + Connect
  `AvroConverter`:** Avro schema would be *inferred* from JSON — record
  name/namespace wouldn't match `dev.sandbox.avro.OrderCreated`, `decimal`
  amounts lose their logical type, nullability guessed. Exact-match lookup
  fails with auto-register off; enabling it reverses M2's reviewed-schema
  decision. Breaks the contract.

### D2 — Outbox rows: keep + retention purge (built in M3)
Rows retained for a retention window (e.g. 7 days), then removed by a
scheduled `DELETE ... WHERE created_at < now() - interval`. Time-based
partitioning + `DROP PARTITION` noted as the high-volume evolution.
- **Why:** audit/debugging trail; DoD ("row in `outbox_events`") and the
  step-6 Testcontainers assertion work as written.
- **Purge job built in M3**, not deferred — an outbox that grows forever
  is the kind of shortcut this project exists to avoid.
- **Rejected — insert + delete in the same TX:** no cleanup job and no
  growth, but no audit trail, and no row to assert after commit → would
  force the fast Postgres-only test into a Kafka-level E2E test.

### D3 — `outbox_events` columns and types
```sql
CREATE TABLE outbox_events (
    id              UUID          PRIMARY KEY,
    aggregate_type  VARCHAR(255)  NOT NULL,
    aggregate_id    VARCHAR(255)  NOT NULL,
    type            VARCHAR(255)  NOT NULL,
    payload         BYTEA         NOT NULL,
    created_at      TIMESTAMPTZ   NOT NULL DEFAULT now()
);
CREATE INDEX idx_outbox_events_created_at ON outbox_events (created_at);
```
- **snake_case** column names (Postgres convention, consistent with
  `orders`), mapped via the Event Router's `table.field.event.*` options —
  over the router's default `aggregatetype`/`aggregateid` (zero config, but
  inconsistent naming).
- `id` **generated by the application**, not a DB default — event identity
  is the producer's; available for logging/tracing before commit.
- `aggregate_id` = `orderId` → message key, same as M2 → per-order
  partition ordering preserved.
- **No `published` flag** — CDC needs nothing marked.
- `created_at` + index → retention purge (D2) and debugging.
- Routing (step 7): e.g. `aggregate_type = 'order'` +
  `route.topic.replacement = ${routedByValue}-events` → `order-events`.

### The dual-write problem
Saving an order to Postgres and then calling `kafkaTemplate.send()` is two
writes to two independent systems — no single transaction spans both.
`@Transactional` only governs the DB connection.

| Failure | Result |
|---|---|
| DB commits, Kafka send fails | Order exists, no event — silently lost to downstream |
| DB commits, app crashes before/during send | Same |
| Send first, then DB commit fails | Phantom event for an order that doesn't exist |
| Send times out (but actually landed), DB rolled back | Phantom event |

Reordering the writes only changes which inconsistency you get.

Why the obvious fixes don't work:
- **Retry the send** — doesn't survive a crash.
- **Send in an after-commit hook** — narrows the window, doesn't close it.
- **Kafka transactions / EOS** — atomic Kafka-to-Kafka only; can't enlist a
  Postgres write.
- **XA / 2PC** — Kafka doesn't support XA; industry avoids 2PC anyway
  (couples availability, holds locks across network round-trips,
  coordinator is a failure point).

### The Transactional Outbox
Write to **one** system: insert the event as a row in `outbox_events` in
the **same local transaction** as the `orders` insert — atomic, both or
neither. A separate relay moves outbox rows to Kafka; if it crashes, the
rows are still there.

Trade-off: the relay can publish and crash before recording progress →
republishes on restart. Outbox gives **at-least-once**, not exactly-once.

Two relay styles:
1. **Polling publisher** — scheduled `SELECT ... WHERE published = false`,
   send, mark published. Simple, but polling load/latency, tricky with
   multiple instances.
2. **Log tailing (CDC)** — read the DB's transaction log; no polling, no
   flags, relay isn't app code. **M3 uses this (Debezium).**

**Q: If we only use the Outbox pattern, can it duplicate data without
idempotency?**
Yes — the outbox produces **duplicate messages**, which become **duplicate
effects** only if consumers aren't idempotent. The DB side never
duplicates (one row per event); duplicates appear in Kafka. This isn't
Outbox-specific — any at-least-once Kafka system redelivers (producer
retries after an ambiguous timeout; consumer crash/rebalance before
offset commit). So consumers must be idempotent regardless; the Outbox
just doesn't remove that need. Industry pairs it with the Idempotent
Consumer ("inbox") pattern:
- **Naturally idempotent ops** — `SET status = CONFIRMED`, upsert by key.
- **Dedup by event ID** — each outbox row has a unique ID carried with the
  message (Debezium's Outbox Event Router puts it in a header); the
  consumer records processed IDs in a `processed_events` table **in the
  same TX as the business effect** and skips IDs already seen.

Net: "event might be lost or phantom" (unfixable downstream) is traded
for "event might arrive twice" (cheaply fixable downstream).

### Change Data Capture (CDC)
Observing row-level changes in a DB and emitting each as an event.

| Approach | How | Problems |
|---|---|---|
| Query-based | Poll `WHERE updated_at > last_seen` | Misses deletes and intra-window changes, query load, clock precision |
| Trigger-based | Triggers copy changes to a shadow table | Extra write per TX, logic hidden in the DB |
| **Log-based** | Read the DB's transaction log | Needs DB config/permissions — otherwise none of the above |

Log-based is the industry standard and what Debezium does.

### Postgres WAL, logical decoding, replication slots
- **WAL (write-ahead log)** — every change hits this append-only log
  before table files; a commit is durable once its WAL record is flushed.
  Used for crash recovery and to stream replicas. Already a complete,
  ordered history — CDC is just another reader.
- **Logical decoding** — turns physical WAL ("bytes on page X") into
  logical row changes ("INSERT into `outbox_events` ..."). Needs:
  - `wal_level = logical` (default `replica` isn't enough) — one line in
    `docker-compose.outbox.yml`
  - an **output plugin** — `pgoutput`, built into Postgres 10+, Debezium's
    default; no extension to install
  - a **publication** — which tables get decoded; for us only
    `outbox_events`
- **Replication slot** — Postgres-side bookmark of a consumer's WAL
  position (LSN). Consumer resumes from it after a crash (no gaps; also
  the source of redelivery if progress wasn't confirmed yet).
  **Gotcha:** Postgres keeps WAL until every slot confirms it — an
  abandoned slot grows WAL until the disk fills. Monitor slot lag
  (relevant for M9).

Why it fits the Outbox: logical decoding emits **only committed
transactions, in commit order** — rolled-back outbox inserts never appear
(no phantoms), committed ones appear only after the order is durable, and
no `published` flag or cleanup query is needed.

### Debezium — what it is and why it's used
Open-source (Apache 2.0) log-based CDC platform. Reads a DB's transaction
log, decodes committed changes, publishes them as events. Connectors for
Postgres, MySQL/MariaDB, SQL Server, Oracle, MongoDB, Db2, others.

What it does with Postgres:
1. Connects as a logical replication client (publication + slot,
   `pgoutput`).
2. Optional initial **snapshot** of existing rows (`snapshot.mode`) — for
   an outbox table, history usually doesn't matter; decide in step 7.
3. **Streams** every committed change as one event.
4. **Tracks position** — stores last-processed LSN as a Kafka Connect
   offset, confirms it back to the slot so Postgres can free WAL. Resumes
   from the last stored offset after a crash → at-least-once redelivery.

Raw event shape: topic `<prefix>.<schema>.<table>`, envelope with
`before` / `after` / `source` (lsn, txId, table…) / `op` (`c`/`u`/`d`/`r`)
/ `ts_ms`. Fine for table replication, **wrong shape for domain events**
(consumers want `OrderCreated` keyed by order ID) → Outbox Event Router
SMT reshapes it.

Deployment modes:
| Mode | What | When |
|---|---|---|
| **Kafka Connect source connector** | Plugin in a Connect cluster | Standard when target is Kafka — **ours** |
| Debezium Server | Standalone app, non-Kafka sinks | Messaging isn't Kafka |
| Debezium Engine | Embedded library | Niche; you own offsets/failover |

Why it over alternatives:
- **Hand-written polling publisher** — legitimate, but polling
  load/latency, published flags + cleanup, multi-instance coordination,
  relay logic back in the service.
- **Hand-written logical-decoding consumer** — reimplements snapshots,
  slots, offsets, reconnects, schema changes, failover edge cases.
- **Kafka Connect JDBC Source** — query-based CDC, inherits its problems.
- **Managed cloud CDC** (AWS DMS, Confluent Cloud…) — valid in production;
  several are Debezium under the hood.
De facto standard for log-based CDC into Kafka; Outbox Event Router is
first-class.

Costs:
- Another component to run (Connect cluster, config, monitoring).
- DB privileges: connector user needs `REPLICATION` + publication
  rights — use a dedicated least-privilege user, not the app's.
- Replication slot monitoring (WAL retention gotcha).
- Outbox table schema becomes a contract with the Event Router.
- Effectively at-least-once — Kafka Connect exactly-once source support
  (KIP-618) only covers what lands in Kafka; consumers still need
  idempotency.

### Kafka Connect
Framework shipped with Apache Kafka for moving data between Kafka and
external systems via **config**, not hand-written producer/consumer code.
- **Source** connectors: external → Kafka (Debezium Postgres is one).
- **Sink** connectors: Kafka → external (not needed in M3).

| Concept | What |
|---|---|
| Worker | JVM process running Connect; hosts connectors/tasks |
| Connector | Plugin + config; decides what to copy, splits work into tasks |
| Task | Moves the data. Debezium Postgres = **always 1 task** (one slot = one sequential stream) |
| Transform (SMT) | Per-message in-flight modification |
| Converter | Serializes key/value to bytes (JSON, Avro + Schema Registry, Protobuf, bytes…) |

Source pipeline:
`Postgres WAL → Debezium task → record → [SMT chain] → converter → topic`,
with the offset (LSN) stored by Connect.

Modes:
- **Standalone** — one process, offsets in a local file; dev only.
- **Distributed** — worker group, state in three internal Kafka topics
  (`config`, `offsets` — Debezium's last LSN, `status`); tasks rebalance
  on worker failure. **Production standard — we use it even with one
  worker.**

Managed via REST API (default port **8083**): `POST /connectors`,
`GET /connectors/<name>/status`, `PUT .../config`, `POST .../restart`,
`PUT .../pause`. Connector config = versioned JSON file in the repo,
posted from a file (PowerShell inline-JSON gotcha). Kafka UI can attach
to Connect to show connector status.

**Converter = wire format** → since M2 publishes `OrderCreated` as Avro
via Schema Registry (and M4's `query-api` will expect it), the outbox
`payload` + Event Router + converter must produce the same Avro contract.
Real design decision → outbox table design topic.

Step-7 heads-ups (not decisions yet):
- Image: `quay.io/debezium/connect` — Docker Hub Debezium images are no
  longer maintained.
- Confluent Avro converter is **not bundled** in the Debezium image — needs
  adding (typically a small custom Dockerfile) if we go Avro + Schema
  Registry; classic "class not found" source.

### SMTs (Single Message Transforms)
Small, **stateless, per-record** functions applied by Kafka Connect,
enabled purely via connector config (`"transforms": "a,b"` — chained in
order, order matters). For source connectors they run **after the
connector, before the converter** → operate on structured data, not bytes.
Built-ins: `InsertField`, `ReplaceField`, `MaskField`, `ValueToKey`,
`ExtractField`, `RegexRouter`, `Filter`; **predicates** apply an SMT
conditionally.

Limits: one in → zero or one out; no joins/aggregation/reliable external
calls. Industry rule: **lightweight reshaping/routing only, never business
logic** (hard to test/version in connector config) — heavier work belongs
in Kafka Streams/Flink or a consumer.

### Outbox Event Router SMT
`io.debezium.transforms.outbox.EventRouter` — turns a raw "row inserted
into `outbox_events`" change event into a clean domain event.

| Outbox column (default) | Becomes | Why it matters |
|---|---|---|
| `id` | Header `id` | Unique event ID → idempotent-consumer dedup key |
| `aggregatetype` | **Topic** (`route.by.field` + `route.topic.replacement`) | Default → `outbox.event.Order`; we configure **`order-events`** to keep M2's topic contract |
| `aggregateid` | **Message key** | Same order → same partition → per-order ordering (Kafka's only ordering guarantee) |
| `type` | Event type; optionally a header (`table.fields.additional.placement`) | Consumers distinguish `OrderCreated` / `OrderConfirmed` without parsing |
| `payload` | Message **value** | The domain event itself, no envelope |

Column names configurable (`table.field.event.id`, …); staying near
defaults = less config.

Behaviors that shape the table design:
- **Insert-only**: updates ignored (warning), deletes ignored or
  tombstoned per config → enables **insert + delete in the same TX**
  (WAL keeps the insert, Debezium publishes it, table stays empty, no
  cleanup job). Alternative: keep rows + scheduled purge. → decision in
  table design topic.
- `expand.json.payload`: parse a JSON-string payload into a structured
  value — relevant to the Avro decision.

Why an SMT over alternatives:
- Consumers read the raw envelope → leaks the producer's **table
  structure** into every consumer; renaming a column breaks them.
- Separate Kafka Streams reshaper → extra component, intermediate topic,
  latency, for purely mechanical work.
- **SMT** → reshape at the edge, inside the component already relaying.
  Consumers see clean domain events on `order-events`, same as M2's
  direct publish → **from a consumer's view, M3 changes nothing.**

### Outbox table design — constraints that drove it
Three settled constraints shaped D1–D3 (see Decisions & trade-offs):
- Avro + Schema Registry mandatory, `auto.register.schemas=false`
  (schemas registered by hand as a reviewed step — M2).
- M2's wire contract: `OrderCreated` on `order-events`, keyed by
  `orderId`, `decimal` logical types for amounts — consumers must see no
  difference.
- Hexagonal: Avro classes stay out of `domain/`; mapping/serialization
  happens in the outbox adapter.

Key insight: the **converter** decides the wire format, so the payload
format is a contract decision, not a config detail. Storing JSON and
letting Connect produce Avro means the schema is *inferred from data*
rather than *defined by the `.avsc`* — fine for ad-hoc CDC, wrong when an
explicit, reviewed Avro contract already exists.
